## What is being compared

Four setups get the identical prompt in an identical fixture project, and only one thing
changes between them: what guidance the agent has. Model, tool access, fixture contents and
graders are held constant. The fixture is the shared [`../../fixtures/`](../../fixtures) six-task
project, forked verbatim.

**`no-skill`** — vanilla Claude Code in a real taskmd project: the `taskmd` binary,
`.taskmd.yaml`, `.taskmd/` templates, and the `tasks/CLAUDE.md` + `TASKMD_SPEC.md` that
`taskmd init` writes. *How far does a competent agent get on its own?*

**`plugin-skill`** — plus `claude-code-plugin/skills/list-tasks/SKILL.md`, which is four lines
long and amounts to "run `taskmd list $ARGUMENTS`, then present the output."

**`lite-skill`** — plus `claude-code-plugin-lite/skills/list-tasks/SKILL.md`, the CLI-free
variant: glob the task files, parse frontmatter, apply the filters yourself, print a table.

**`bare-project`** — no skill *and* no taskmd: `.taskmd.yaml`, `.taskmd/`, `tasks/CLAUDE.md`
and `TASKMD_SPEC.md` deleted, and a stub `taskmd` first on `PATH` that exits 127. Only the six
markdown files remain. *How much of the result comes from the skill versus from taskmd's own
scaffolding?*

## Bottom line

**The lite skill is the clear winner at 100%, and the "0% delta" recorded under the old
`benchmark/` harness was wrong.** That earlier result concluded the skill added nothing because
Claude finds `taskmd` on `PATH` anyway. It does — but finding the CLI was never the hard part.
Two failure modes it never probed account for 22 of this run's 31 failures:

1. **Without a skill, "which of my tasks are still pending?" is not understood as a question
   about the project at all.** In 14 failures the agent ran exactly one command —
   `cat ~/.claude/projects/<workdir>/memory/MEMORY.md` — found no memory file, and asked the
   user where their tasks live. It never ran `ls`. Either skill eliminates this completely.
2. **The plugin skill destroys output format fidelity.** Asked for JSON, it fetches correct
   JSON from the CLI and then re-renders it as a markdown table, 8 times out of 8.

## Failure analysis

All 31 failures, classified. No variant ever mutated the fixture and no sample touched a
forbidden tool (see Hermeticity).

| Mode | Count | Who |
|------|-------|-----|
| **A** — looked in Claude's own memory instead of the project | 14 | `no-skill` 8, `bare-project` 6 |
| **B** — right data, wrong format (markdown table instead of JSON) | 8 | `plugin-skill` 8 |
| **C** — treated `critical` as "high priority" | 5 | `bare-project` 5 |
| **D** — counted `in-progress` / `completed` as "pending" | 4 | `bare-project` 3, `plugin-skill` 1 |

### A — "my tasks" resolves to Claude's memory, not the project (14)

The single most consequential finding, and it is perfectly consistent: **all 14** ran exactly
one command, `cat ~/.claude/projects/<workdir-slug>/memory/MEMORY.md`, and **none** ever
referenced `tasks/`, `taskmd` or `.taskmd`. Typical answer:

> I don't have any pending tasks tracked for you—memory is empty and there's no prior context
> in this session. Could you tell me what tasks you're referring to (e.g., a specific project,
> a TODO list, or a task tracker like Linear/GitHub)?

It is **phrasing-dependent, not project-dependent**. The same `no-skill` variant in the same
workspace scores 8/8 on `list-all`, where it immediately runs `ls -la`, reads `TASKMD_SPEC.md`
and `tasks/CLAUDE.md`, and then runs `taskmd list`. The trigger is the request wording:

| Prompt | `no-skill` |
|---|---|
| "show me all my tasks" | 8/8 |
| "what's on the plate for the CLI?" | 8/8 |
| "what's in the mvp phase?" | 8/8 |
| "which of my tasks are still pending?" | **2/8** |
| "list my high priority tasks as JSON" | 6/8 (2 of the misses are mode A) |

"mvp phase" and "the CLI" are unmistakably about this project, so the agent grounds itself.
"still pending" and "high priority" are generic assistant-todo vocabulary, and it resolves them
against its own memory instead. Both skills fix this outright — 0 mode-A failures between them —
which is precisely the value the deprecated harness failed to detect.

### B — the plugin skill discards the requested format (8/8)

The one hard, fully reproducible skill defect in this run. The agent runs the right command and
gets the right three tasks, then renders them as a markdown table and signs off with a claim
that is false from the user's side of the screen:

> | ID | Title | Status | Owner | Group |
> |---|---|---|---|---|
> | 001 | Fix login SSO bug | in-progress | alex | cli |
> | 005 | Refactor authentication module | completed | alex | cli |
> | 006 | Export reports to CSV | pending | jordan | web |
>
> Raw JSON is above in the tool output if you need to consume it directly.

The JSON was in the *tool* output, which the user never sees. The skill's entire instruction for
this is step 2: *"Present the output to the user."* `lite-skill` passes 8/8 here and `no-skill`
6/8, so this is the skill making the agent **worse** than no skill at all.

### C, D — enum words read as English (9)

`bare-project` treats `pending` as "not finished" (folding in `in-progress`) and `high priority`
as "important" (folding in `critical`). Both are reasonable English readings and both are wrong
against taskmd's enums — `status` and `priority` are closed value sets, which is exactly what
the stripped `TASKMD_SPEC.md` would have said. This is the variant working as designed: it
prices taskmd's own scaffolding. The single `plugin-skill` mode-D failure is different — on
`list-scope-filter` it answered the *pending* question instead of the CLI-group one.

**Grading note, stated plainly:** modes C and D are graded against the CLI's semantics
(`--status pending` and `--priority high` are exact matches), and a human might accept the
broader reading. The evals were specified this way deliberately, but a reader should know that
5 of `bare-project`'s 14 failures turn on that judgment call. `no-skill`'s and
`plugin-skill`'s numbers do not depend on it.

## Cost and latency

`plugin-skill` is the cheapest and fastest by a distance — **30% cheaper and 2× faster** than
`no-skill` — because it does one thing: runs `taskmd list` and stops. Median 283 total tokens
against ~1,100 for every other variant.

`lite-skill` buys its perfect score with effort: 241 `Read` calls and 57 `Glob` calls across 40
samples, versus 49 `Bash` calls total for `plugin-skill`. It costs the same as no skill at all
($0.154 vs $0.145) and is only marginally faster. It re-implements the CLI in the agent loop,
and the token bill says so.

## Hermeticity

Clean, by two independent means:

- **`tool_not_used` passed on all 160 samples.** No variant reached `Skill`, `TaskCreate`,
  `TaskUpdate`, `TaskList`, `TaskGet` or `ToolSearch`.
- **A manual census of all 160 conversation logs** found only `Read`, `Bash`, `Glob` and `Grep`
  — the declared `allowed_tools`. No `Write` or `Edit`, though both were reachable.

The per-variant tool profiles above are also a sanity check that the variants really differ:
`plugin-skill` is Bash-only (it drives the CLI), `lite-skill` is Read/Glob-dominated (it parses
files), exactly as each skill instructs.

**`no-mutation` passed on all 160 samples** — every one of the 31 failures was a `check_output`
failure. Nothing edited, reorganized or "helpfully" completed a task while answering a question
about it. `Write`/`Edit` were deliberately left reachable so this check could fail; it never did.

## Grading

Correctness is graded from the agent's reported answer, not the filesystem — `list-tasks`
mutates nothing, so the `add-task` approach of inspecting a created file does not transfer.
skival's `check_output` pipes the agent's final text to a stdlib-only Go grader on stdin
(`../workspace/.verify/`), which asserts the exact expected ID set two-sided: every wanted task
present, no other fixture task present.

Two grader bugs were found and fixed **before** this run's numbers were trusted; both are pinned
as regression cases in `workspace/.verify/output_test.go`, which exercises every grader in both
directions at zero token cost:

1. A correct answer that closed with *"The other two tasks (006 export CSV, 004 update README)
   are in the Polish phase, not MVP"* was scored as leaking 004 and 006. Cue-word blocklists
   lose this game — that sentence contains none. The fix is structural: when an answer contains
   list items, only those lines count and prose is commentary.
2. Rows labelled by group path (`web/003`, `cli/001`) were not recognised as list items. Fixed
   after the run; **re-grading all 160 recorded outputs produced zero verdict changes**, so
   every number above is unaffected.

A caveat worth stating: exact-set matching on free-form prose is a heuristic, and the honest
gap noted in the task file remains — skival has no verifier that natively expresses "exactly
this set". The graders here work around it rather than closing it.

## Recommendations

See [../SUGGESTIONS.md](../SUGGESTIONS.md). In short: fix the plugin skill's format handling (it is a
two-line change and worth ~20 points of pass rate), and do not read `plugin-skill`'s 77.5% as
"worse than no skill" — on everything but JSON it is 97% against 81%.
