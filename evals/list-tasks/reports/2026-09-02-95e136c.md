## Bottom line

**The format fix worked, completely.** `plugin-skill` went from 0/8 to **8/8** on the JSON eval
and has **zero failures across all 40 samples**. It is now ranked #1 on correctness *and* cost
*and* latency simultaneously — 100%, $0.11 per sample, 10.9s, against `lite-skill`'s 95% at
$0.16 and 18.4s.

**But three variants moved that should not have.** `no-skill` and `bare-project` contain no
skill file at all, so their inputs were byte-identical between runs, and they still shifted by
−17.5 and −7.5 points. That is the headline caveat on everything below: **this suite's
run-to-run variance is much larger than its within-run confidence intervals suggest.**

## Did the fix cause the improvement?

Yes, and the evidence is mechanistic rather than statistical — which matters, because the
controls drifted by more than a naive reading of the confidence intervals would allow.

- The change was targeted at exactly one eval, and that eval went **0/8 → 8/8**.
- The failure had a single, fully consistent signature in run 1 (fetch correct JSON, re-render
  as a markdown table, claim "raw JSON is above in the tool output"), and that signature is
  **absent from all 8 samples** now. The agent emits the CLI's JSON verbatim in a fenced block.
- The command it runs is unchanged — `taskmd list --priority high --format json` in both runs.
  Only the presentation step moved, which is the only thing the edit touched.

A +22.5 point swing on a variant whose controls moved −17.5 would be weak evidence on its own.
Combined with a named mechanism and a clean 8/8 on the targeted eval, it is not.

## The variance finding

This is the most important methodological result of the run, and it partly undercuts run 1's
precision claims.

`no-skill` and `bare-project` have **no skill file**. Nothing about their configuration changed
between run 1 and run 2 — same fixture, same prompts, same model, same tool list, same graders.
They still moved:

| Variant | Run 1 | Run 2 | Δ | Inputs changed? |
|---|---|---|---|---|
| `no-skill` | 80% | 62.5% | **−17.5** | no |
| `bare-project` | 65% | 57.5% | −7.5 | no |
| `lite-skill` | 100% | 95% | −5.0 | description + enum note |
| `plugin-skill` | 77.5% | 100% | +22.5 | format fix (targeted) |

The driver is failure mode A — the agent resolving "my tasks" to its own memory — which grew
from 14 occurrences to 17 and is concentrated in the two variants with no skill. It is a
**bimodal** behavior: `no-skill` scored 2/8 then 0/8 on `list-status-filter`, and 6/8 then 2/8
on `list-json-format`. Both runs are honest samples of a genuinely unstable baseline.

**Consequence for reading either report:** the reported 95% intervals are within-run binomial
intervals over 40 samples. They do not model between-run drift, and the observed drift on an
unchanged variant (17.5 points) is wider than most of those intervals. Treat a difference of
less than ~20 points between two *runs* as unresolved unless there is a mechanism, as there is
for the format fix. Differences *within* a run, between variants measured side by side, are not
affected by this.

## Was the lite-skill dip a regression from its edit?

**No — tested directly, and it was not.** `lite-skill` fell to 95%, and its SKILL.md had been
edited (widened `description`, added an enum note), so this could not be waved off as noise.
Both failures were the same behavior: dropping task `005` from the results because it is
`completed`, on `list-scope-filter` ("what's on the plate for the CLI?") and `list-json-format`.

The new `description` contains the words "outstanding" and "on the plate", so a priming effect
was a plausible mechanism. An A/B held everything else constant and varied only the skill file —
the pre-change SKILL.md (from commit `bd3a99a`) against the current one, 8 samples on each of
the two affected evals:

| | `list-scope-filter` | `list-json-format` | Total |
|---|---|---|---|
| lite-**pre** (before the edit) | 7/8 | 8/8 | **15/16** |
| lite-**post** (current) | 8/8 | 7/8 | **15/16** |

Identical, and decisively so: the "dropped `005` because it is completed" failure occurred on
the **pre-change** skill. The behavior is pre-existing and intermittent, not introduced by the
edit. It is also arguably defensible on `list-scope-filter` — "what's on the plate" can
reasonably be read as excluding finished work — which makes that eval's prompt the weaker link,
not the skill.

Reproduce with:

```bash
git show bd3a99a:claude-code-plugin-lite/skills/list-tasks/SKILL.md > /tmp/lite-pre/SKILL.md
# then a 2-variant suite pointing `skill:` at each file
```

Mode B is gone. Mode C reaching `no-skill` (3 failures, new this run) is the same enum-vs-English
confusion that only `bare-project` showed in run 1 — more evidence that these baselines wander.

## Recommendations

1. **Ship the format fix.** It is unambiguous, and it makes `plugin-skill` the best variant on
   every axis at once.
2. **Do not trust a single run of `no-skill` or `bare-project`.** Their scores swing by up to
   17.5 points with no input change. If a future comparison hinges on the baseline, run it twice
   or raise `samples`. The skill variants are far more stable.
3. **Reconsider the `list-scope-filter` prompt.** "What's on the plate for the CLI?" is read by
   some samples as excluding completed work, which is a defensible answer graded as wrong. The
   eval currently measures prompt interpretation as much as filtering.
4. Remaining unverified item: the widened `description:`. It is still untestable here, because
   skills are injected as a system prompt and `description:` never decides whether they load.
