## What the skill buys

**22.5 points over `no-skill`, and essentially all of it is one eval.** Both skills go 8/8
on `get-by-keyword` where `no-skill` and `bare-project` go 0/8 — 16 failures, all the same
failure.

The agent answers from its own memory instead of the project. Verbatim, `no-skill`:

> No memory index exists yet, and there's nothing in this conversation about an SSO login
> bug. Could you share more details (ticket link, repo, or description)?

and `bare-project`:

> I don't have any memory of an SSO login bug — the memory store is empty and this is a
> fresh, non-git working directory **with no files in it**.

That last claim is false: `workspace-bare/tasks/` holds all six task files. The agent never
looked. This is exactly the pathology [`list-tasks`](../list-tasks/REPORT.md) documented,
reproduced in a second suite with a different skill, and it confirms the mechanism:

- **`get-by-id`** — *"show me the details of task 003"* — uses project vocabulary and an ID.
  **8/8 for every variant, including the one with no CLI and no docs.**
- **`get-by-keyword`** — *"what's the task about the SSO login bug?"* — uses generic
  assistant vocabulary and no ID. **0/8 without a skill, 8/8 with either one.**

Same fixture, same tools, same model. The variable is whether the question names something
the agent recognises as project state. The skill's value is not teaching a CLI; it is
telling the agent that a question like this is about *files in this directory*.

## Findings

**1. `plugin-skill` is cheapest, fastest, and tied for most correct.** $0.1115 and 12.5s
median against `no-skill`'s $0.1354 and 17.6s. Its tool census is the leanest in the suite
(Bash ×81, Read ×22, Glob ×8 across 40 samples; `no-skill` spends Bash ×106). Reaching for
one command beats exploring. This is the opposite of the `list-tasks` result, where
`plugin-skill` fetched correct JSON and re-rendered it as a table — here it went 8/8 on the
JSON eval.

**2. Stripping taskmd costs almost nothing for this skill.** `bare-project` (80%) is
*above* `no-skill` (77.5%) — a difference well inside the noise, so read it as "no
difference". Compare `add-task`, where `bare-project` fell to 45%. Finding and reporting one
markdown file does not need the CLI; only knowing to look does.

**3. The CLI's fuzzy matcher is an active trap, and the skill does not mention the way
out.** All 8 `plugin-skill` samples of `get-missing` ran `taskmd get 042`, and all 8 got the
interactive selection prompt — `taskmd` fuzzy-matches 002 at 67%, asks for a choice, and
with no tty exits 1 with `Error: invalid selection`. Every sample recovered by falling back
to `taskmd list`, so correctness held at 8/8, but each paid an extra round trip. `--exact`
returns a clean `task not found` and neither skill names it.

The trap needs a short query: `taskmd get "SSO login bug"` scores below the 0.6 threshold
and returns `task not found` cleanly, which is why `get-by-keyword` never hit it.

**4. Four of five evals are at the ceiling.** `get-by-id`, `get-missing`,
`get-json-format` and `get-blocked-state` are 8/8 for all four variants (one exception,
below). Only `get-by-keyword` discriminates. The suite currently measures one thing well
and four things not at all — see [SUGGESTIONS.md](../SUGGESTIONS.md#suite).

**5. The single `get-blocked-state` failure is a lookup failure, not a reasoning one.**
`no-skill` sample 2 answered:

> There's no task 003 — the `tasks/` directory only contains **002** and **004**.

It globbed the root of `tasks/` and never descended into `tasks/cli/` and `tasks/web/`. The
grader's message ("names neither the dependency nor that 003 is blocked") is accurate but
misleading about the cause.

**6. No tool leakage.** Census across all 160 conversations: `Bash`, `Read`, `Glob`, `Grep`
only — every one inside `allowed_tools`. `tool_not_used` passed on every sample.

**7. `no-mutation` passed 160/160 and that result is worth nothing.** Added after the fact,
on discovering what `allowed_tools` actually does: skival compiles it into the claude CLI's
`--tools` flag, an *exclusive whitelist over built-ins*, so `Write` and `Edit` — absent from
this suite's list — were denied at tool registration. The agent could not have mutated the
fixture if it had tried. The suite comment claimed the opposite ("deliberately not added to
`disallowed_tools`… so the agent can still reach them"), inherited from `list-tasks` and from
`evals/README.md`, all of which described a skival that predates commit `8b42dcb`.

Nothing else in this report is affected — correctness is graded from the agent's text, and
`tool_not_used` and the census are independent — but **do not cite `no-mutation` from this run
as evidence that a read-only skill leaves the project alone.** To make it a real assertion,
`Write` and `Edit` have to be added to `allowed_tools`; that changes the variant configuration
and so starts a new baseline, which is why it was not done retroactively here.

## Grader corrections

Three samples were graded wrong by the run and are corrected above. All three were **false
negatives in `get-missing`**, all three are pinned in `output_test.go` with the verbatim
agent text, and all three are fixed in the commit that accompanies this report. Re-grading
all 160 recorded outputs flipped exactly these three and nothing else.

| Sample | Agent said | Bug |
|--------|-----------|-----|
| `no-skill` #1 | *"I don't see a task 042 in this project"* | The not-found cue list had `no task` but not `don't see`. Broadened to cover the idioms of non-existence. |
| `no-skill` #3 | *"There's no task 042 — the highest task ID present is 006 (…006-export-reports-csv.md)"* | The mislabel span broke on sentence punctuation, and an em dash is not that, so 006's title read as attached to 042. The span now also breaks on **another task ID** — if a real ID sits between 042 and a title, the title belongs to that ID. |
| `plugin-skill` #4 | *"There's no task 042. The closest match is **002: Add full-text search**."* | The ID regex consumed the sentence-ending period as part of its match, so the forward span started *after* the boundary and swallowed the next sentence. The digits are now captured and addressed directly. |

All three share a shape: the agent was right and the grader's notion of "attached to 042"
was too loose or its vocabulary too narrow. Two earlier bugs of the same family were caught
before spending — one by the Go tests (`critical-priority` failing to match `critical`), one
by the smoke run.

## Honest caveats

- **These are post-hoc numbers.** They come from re-grading this run's recorded text, not
  from a second paid run. That is sound for `check_output`, which sees only that text, but
  it is not the same as a clean re-run and is labelled as such throughout.
- **`plugin-skill` vs `lite-skill` is unresolved.** Both 40/40; the intervals overlap
  completely. Cost and latency favour `plugin-skill`, and that is the only defensible way to
  choose between them from this run.
- **`bare-project` vs `no-skill` is unresolved** (32/40 vs 31/40). Do not read the ordering.
- **One eval carries the entire result.** With `get-by-keyword` removed, all four variants
  sit at 31/32–32/32. A headline "the skill is worth 22.5 points" is true only for questions
  phrased the way that eval phrases them.
- **Grading judgment calls**, unchanged from [CLAUDE.md](../CLAUDE.md#deliberate-grading-judgment-calls):
  `get-by-keyword` fails an answer that offers 001 *and* 005 as candidates; `get-missing`
  accepts naming a near-match as a near-match; `assertFields` is presence-only. None of
  these affected a sample in this run — no variant produced an answer near those lines.
- **No cross-run comparison exists yet.** This is run 1. `list-tasks` saw variants with
  identical inputs drift 17.5 points between runs, so treat a future single-run delta under
  ~20 points as unresolved without a named mechanism.
